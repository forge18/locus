Chapter 0

Orientation

Locus is a desktop IDE whose primary surface is not an editor. It runs coding agents in disposable containers — one session per container — across many agent harnesses, and gives every one of them the same memory, the same mail, the same board, and the same tools.

What Locus is, and is not

The useful map of the 2026 parallel-agent field has three tiers: Tier 1 in-process subagents, Tier 2 local orchestrators running agents in isolated workspaces on your machine, and Tier 3 cloud async agents. Locus is Tier 2, containing Tier 1, and deliberately not Tier 3.

Nearly every Tier 2 tool solved isolation, because git worktrees made isolation easy. Almost none solved coordination or shared learning. Locus's bet is exactly there: shared memory and agent mail implemented once in Rust and available identically to every harness.

Locus isLocus is not
A single-user local toolA hosted platform or a team service
A control plane; the editor is a pane inside itA VS Code fork or an extension host
One window, one selected project, cross-project views alongsideA window per project
Container-per-run, cloning from a bare local remoteBind-mounted shared worktrees
A CLI surface for agents over a Unix socketAn MCP host. No MCP servers, ever
Postgres as the single storeA file tree of memory, mail, and wiki entries

The three lifecycles

Independent teams have converged on the same decomposition because the three parts have different lifecycles: context changes continuously, capabilities change deliberately, environments are ephemeral. Anthropic calls them Session, Harness, and Sandbox. Knowing which of the three you are touching tells you what a change costs.

Vocabulary you need before anything else

TermMeans

The three rules carried into everything below 1. Nothing in locus-core names a harness — adding one is a trusted plugin manifest, never a match arm. 2. Every harness entry is complete; nothing is inherited, so a descriptor reads cold. 3. The database is derived where it can be — harness output, git, and the marketplace index are sources of truth Locus never writes.

Part I

How Locus works internally

1.1 Process topology

One Tauri application, one Rust core, one Postgres. The core — locusd — also runs headless, which is what makes a scheduled workflow that fires while no window is open a real thing rather than a promise.

Every start reconciles On boot the supervisor compares runs marked running against Docker. Container alive → re-attach its stream. Container gone → close the run as aborted, emit the event, file it in the inbox. Without this, a crash leaves rows claiming to be running forever.

1.2 Containers, images, networks

ContainerLifetimePurpose
locus-postgresper machineThe store. pgvector + tsvector + window functions.
locus-agent-<run_id>per agent runOne harness process, one session. No TUI; ACP over stdio from the host.
locus-svc-<project>-<name>per projectServices the project declares — its own Postgres, Redis, the browser.

Network locus-<project> joins a project's agents and service containers. Agents reach each other and the project's services; they never reach another project. Only two paths are mounted into an agent container, and /workspace is not one of them.

tui = false is required, and the registry enforces it A TUI harness multiplexes several sessions inside one process, which hides them from Locus — it could not display, count, or own them individually. A descriptor claiming tui = true is refused at registration. This preserves the 1:1 mapping between sessions and runs that everything downstream depends on.

1.3 The git model — a local remote, not shared worktrees

Every project has a bare local remote on the host. An agent container clones from it, works, commits, and pushes a branch back. You bring the work into your own repo with ordinary git.

Two honest costs. Overlap surfaces at merge — two agents can edit the same file and resolve it the way every team already does. Clones cost disk and time — mitigated by --reference against a shared object store, so N agents on one repo is not N copies of its history.

Repo modeWhere the code livesYou work through
Linked~/Repos/foo stays yours; Locus syncs with ityour own checkout, and Locus
Managedcloned from the forge, lives only inside LocusLocus only

1.4 Credentials and egress

The requirement, stated before the mechanism: getting a harness authenticated inside a container must be easy to use and secure. The container must not hold a long-lived secret, and setting one up must not be a per-project chore. Spike 1 settled on a host proxy.

The defense layers worth naming

LayerIn Locus
Privilege separationThe tool allowlist is the privilege set. A reviewer agent gets read-only tools and cannot write.
SandboxingContainer per run, no host filesystem, no Docker socket, clone not mount.
Egress controlThe proxy, with per-agent policy tiers.
Rate limitingCap tool calls per run, not only iterations and tokens — injection usually needs volume.
Canary tokensA secret string in the materialized config that must never appear in output. If it does, the system prompt leaked.
Anomaly detectionEvery run's tool sequence is already normalized in Postgres, so "unlike this agent's baseline" is a query.
Human in the loopGate nodes and locus ask, calibrated to what is irreversible, touches production, or reaches credentials.
Stated honestly Containers share the host kernel. This is weaker isolation than a microVM — Docker moved its own sandbox product to microVMs for exactly that reason. Containers are the pragmatic choice on Linux and macOS with no proprietary dependency, but the boundary is a kernel boundary, not a hypervisor one.

1.5 The one surface — eight extension types

An extension is authored once, in Locus. At run start the core reads the selected harness plugin's descriptor and writes that extension into the path and file format the harness expects, under /locus/config, for that run only.

ExtensionIsConsumed by
agentsagent definitions — frontmatter over prosethe harness
commandsinvocable prompt templates; worth writing only when they take argumentsthe harness
hooksshell scripts declaring their events; JSON in and out, exit 0 alwaysthe harness
lintersa check plus the rule saying why, per directorylocus lint — not the harness
output-styleshow the agent writes; one is active per harnessthe harness
rulespath-scoped instructions, loaded when a matching file is touchedthe harness
skillsSKILL.md per directory, model-invocablethe harness
base-contextthe always-loaded instructions every session starts withthe harness

Two of the eight do not behave like the rest, and every descriptor has to say so. linters are tool-facing — no harness reads them, so every harness supports them trivially and identically. output-styles is the most divergent — where a harness has no mechanism, the style is folded into base-context and the descriptor records the loss.

base-context is near-uniform in practice (AGENTS.md almost everywhere), which is why it also serves as the fallback injection path for harness plugins that cannot inject at session start.

1.6 Materialization — the code half of the contract

Declaring where an extension goes is not enough. A harness with no rules directory needs its rules turned into something it does read, and that is a transformation, not a path. Because Locus builds a whole config tree per run and destroys it after, materializers generate whole files: no markers, no merge, no prune, nothing to reconcile.

Naming the loss

A rule folded into always-on context is not the same thing as a rule the harness loads when a matching file is touched. An entry that hides the difference is how you end up believing in a capability you do not have — so a downgraded strategy carries weaker_than_native:

rules = { via = "merged-into", target = "context", strip_frontmatter = true,
          weaker_than_native = "always-on; path scoping is lost" }

Native and downgraded counts shown anywhere in the UI are computed from the registry: registered harnesses × eight extensions is the denominator, and the numerator counts weaker_than_native keys. Registering a user harness moves the number without an edit.

1.7 ACP and the canonical event vocabulary

The Agent Client Protocol — JSON-RPC 2.0 over stdio, LSP-for-agents — is the only interface an agent session speaks to Locus over. One container hosts one ACP conversation, and the UI renders its normalized events. There is no terminal on the agent path; human terminals remain available for hand work only and are never agent sessions.

Two constraints that survive the choice session/new accepts only cwd and mcpServers, so a client cannot inject a system prompt. Prompt assembly belongs entirely to the harness; base-context, skills, rules, and tools reach the agent through the materialized config tree instead. And mcpServers is passed empty — always.
permission_request is posture-aware In the default bypass posture every harness gate is switched off at launch, so a permission_request is a misconfiguration alarm. In a dispatch-selected gated posture the same event is a visible human-action request that blocks until resolved. The run's stored posture, not the verb alone, determines its meaning.

1.8 Sessions, runs, turns

"Session" is overloaded — ACP has sessions, every harness has sessions, the UI has panes. Locus needs one definition, and the split exists for exactly one reason: the session is what survives the reset.

Handoffs — a payload, not a transcript

Guardrails kill and reassign after three stuck iterations, and a session belongs to exactly one agent. Work therefore changes hands regularly, and without a payload the successor inherits a branch and a task and rediscovers everything else. locus handoff <agent> --why … ends the current session and opens a new one on the same task and branch, carrying:

FieldHolds
goalwhat this work is for, restated
done[]what is finished, each with the evidence
remaining[]what is not, in the order it should be taken
attempted[]what was tried and did not work — the expensive half, and the reason the mechanism pays for itself
decisions[]choices already made, so they are not re-litigated
open[]questions the successor inherits

A handoff is not mail and not locus agent invoke. Mail is a message between agents that both keep working; invoke is a nested run that returns to its caller. A handoff transfers ownership and does not come back.

1.9 The store, and the fold

Postgres is the single source of truth, in nine schemas. Harness output, git, and the marketplace index are sources of truth outside Locus and are never written by it. Board, wiki, memory, and mail are the exception — they exist only in Postgres, which is why backup is a requirement rather than an afterthought.

SchemaHolds
coreprojects, repos (multi-repo per project), local remotes, settings
agentsversioned agent_defs, sessions, runs, parent/child run edges, normalized events, artifacts and their comment threads
boardtasks (fixed columns, blocked as a status), dependency edges, transitions, assignments, task↔run links, evidence, linked forge issues
wikityped pages, revisions, links, contradictions, ingest log, embeddings
memorycore (bounded, materialized per run) and store (facts, scope, provenance, embeddings, confidence, decay)
workflowsversioned workflow_defs (graph + spec JSONB), schedules, executions, iterations, guardrail trips, verify results
mailthreads, messages, delivery state
marketmanifests, installs, per-image tool sets
logentries — Locus's own domain event log; the only table any of the above is written from

1.10 Memory

Four layers, split by lifetime. Locus owns three; the one it does not own is the one every memory product tries to build twice.

LayerLives inDies whenOwnerShared
Workingthe context windowthe run endssub-harnessno
Short-termprobation bufferpromoted, or aged outLocusno
Long-termPostgresdecays below thresholdLocusyes, by role
Writtengit — artifactsneverthe repoeveryone
There is no shared short-term Two agents sharing scratch state is a documented failure mode: two writers sharing one home compound each other's entries into state neither of them authored. Sharing begins at long-term, after consolidation, so the promotion boundary and the trust boundary are the same line.

Recall depth reverses by task class

This is the counter-intuitive result the design is built around. On factual QA, accuracy rises monotonically with k. On agentic tasks the sign flips — success falls from 32.1% at k=1 to ~25% at k=5, and flat retrievers drop below the 22.4% no-memory baseline. Over-retrieved agents do not simply fail; they wander.

Task classSubstratekGraph expansion
Code generation / editflat, similarity only1off
Planning / strategydistilled procedural cues1off
Research / reviewstructural, hierarchicalhighon

task_class: code | plan | research sits on the agent definition, defaulting to code; a workflow's Agent node overrides it per role. Turn-level body injection is off for code and plan — a missed injection costs one tool call, while a wrong one measured below the no-memory baseline.

Memory is not the wiki

The wiki is curated prose a human reads and reviews. Memory is what an agent recalls: scoped facts with provenance, embeddings, and decay. They share pgvector and nothing else. Two more kinds of knowledge are deliberately not memory: code structure (AST-derived, queried live via codanna) and the project constitution (small, always loaded, and human-written — LLM-written context files measure ~3% worse at 20%+ more cost).

1.11 Token discipline

If token usage explains most of the variance in how a run goes, tokens are not an operational concern that gets attention when a bill arrives — they are a design constraint on every surface that puts bytes in front of a model. Four levers, in the order they pay.

Part II

Using Locus

2.1 The shell and the address space

One window, one selected project, and a group of views that are explicitly not scoped to it. A window per project would rebuild the thing the design exists to remove: one inbox per window, one place per window to notice an agent has been idle for an hour.

Nine categories, in two groups

Manage projectthe board and its sessions, as kanban, list, dependency graph, or timelinewhat is assigned, and what is running

Manage operates; Workshop authors An agent you are assigning work to and an agent definition you are editing are different activities on the same object — one is a thing doing work, the other is a document under version control. The same holds for workflows: the canvas is Workshop, a running execution is Manage. That is why agents and workflows appear twice in the rail and it is not a duplication.

One address space, so there is one resolver

locus://<project>/session/<id>[/run/<id>]
locus://<project>/task/<id>       artifact/<id>       page/<slug>
locus://<project>/workflow/<id>[/execution/<id>]      agent/<name>@<version>

The command palette, global search, inbox items, board-card links, artifact comments, notification deep links, and a detached window's identity are otherwise seven navigation paths that drift apart. Against one locator they are one resolver with seven callers. Cmd-K resolves a locator; Cmd-P searches for one; back/forward per window is a stack of them. resolve(locate(v,p)) == (v,p) is asserted, not assumed.

2.2 Setup — configuring a project

Three tabs: Settings, Persistence, Analytics.

Settings — five panels

PanelWhat it controls, and the rule that binds it

The picker draws only from harness plugins configured in Workshop → Plugins.

2.3 Plan — a guided conversation that produces a reviewable spec

Three agents, not one. The split is structural: measured on ProgramBench, single-pass agents terminate early by their own choice at a median of 22–177 turns, because exploration and implementation compete for the same attention and implementation wins. Splitting them lifted test pass rates 6.9–21.3% relative.

2.4 Manage — the board and its sessions

Fixed columns across every project, deliberately not configurable, and only the gating something else already depends on.

Manage offers four views over one toolbar. Kanban carries card decoration sourced from the task fold and its evidence — a live pulse with the running token count, a blocked marker naming the gate, a stuck 3/3 ring from the guardrail, the verify command on Testing cards, the gate name on Reviewing cards, and the evidence summary on Done. List pairs active and inactive sessions with a live detail pane, including the stuck-guardrail banner and its Hand off control. Graph draws the dependency DAG, where every edge is one board.task_dependencies row and there is no edge with no row. Timeline is the same tasks against wall-clock.

Evidence proves the requirement was met, not that the feature is right A deployment report describes a payments backend that passed CI in two cycles against an adversarially-written suite and still shipped two business-logic failures, because neither behavior was in the contract. No amount of verification reaches outside its requirement. This is why the planning module's elicitation, not its audit, is where the quality actually comes from.

2.5 Interact — sessions the board never sees

A container, a branch, and an agent you talk to directly. No card, no plan, no gate — the escape hatch every plan-driven system needs, and honest about its cost: nothing there is reviewed, so nothing reaches main from it until you promote it or land the branch yourself.

2.6 Review, Analytics, and Memory

Review is now; Analytics is after. Review says what is broken in this project — a failing test, a linter violation, an LSP diagnostic, a reviewer's finding. It is a scheduled or manual aggregated pass, never a stream: sending a finding to the inbox tracks it as a to-do and leaves it listed where it was found. Keeping the two apart stops Review growing into a query tool and stops Analytics growing a live view nobody watches.

Analytics ignores the project filter entirely, because cross-project questions are the useful ones and a spend chart that silently showed one project would be worse than no chart.

Memory is where the four knowledge homes become inspectable:

ScreenShows
Short-termThe context window as an anatomy, not a cache: "nothing here is stored — it is rebuilt from scratch every iteration." Resident items list in fixed prefix order, because the order is the cache. Each row carries a size and a tag: cached, re-read, volatile. Compacted out is the bridge to artifacts.
Long-termFacts in one of four confidence states — verified · asserted · decaying · contradicted. Provenance beats recency: a passing verify outranks any later assertion. Editing a recalled fact does not overwrite it — the written fact stays revision 1, the correction becomes revision 2, and provenance still points at the run that wrote revision 1.
WikiTyped pages: source, entity, concept, synthesis, decision, overview. Ingest, not authoring is the entry point. A contradiction is flagged at ingest, not at query, as a card offering Adjudicate and Board card. locus wiki lint reports orphans, broken links, entities never given a page, and assertions with no source.
ArtifactsPlans, diffs, diagrams, images, recordings, walkthroughs — commentable, and a comment steers the agent that made it.
MailThreads between agents, the mail wait timeout, and handoff payloads.

Artifacts — two representations, because a human and a model want opposite things

KindStoredAgent-facing
imageWebP q80, longest edge capped at 2560OCR text if the shot carries text; otherwise downscaled to 1500px
recordingWebM as the browser produced it, capped by durationextracted keyframes, never the clip
diff · plan · walkthroughtext in Postgresthe same text

An error dialog, a terminal capture, or a failing assertion is text wearing a screenshot's clothes. Only appearance — a layout, a rendering bug, a diagram — justifies sending pixels. Media has a retention policy (pruned with its run after 30 days unless linked to a PR or a task in Done); text artifacts are small enough to keep forever, and the trace depends on them surviving.

The kinds also split by whether a human is meant to see them. Review kinds (plan, diff, diagram, image, recording, walkthrough) reach the inbox when they need you. Reference kinds — finding and payload — never do; they are storage with a handle. Without that split the inbox fills with an agent's own scratch, and the one surface built to protect your attention becomes the one that spends it.

2.7 Dispatch — a durable queue, and the rate a human can absorb

A card being ready is not the same as a card being started. Dispatch is the queue between them, and it is supervisor state rather than UI state — caps, ordering, autorun, schedules, and the kill switch all survive a restart, because a queue that forgets is a queue that double-starts.

2.8 The inbox

With N agents running, your attention is the bottleneck. Everything that needs you arrives in one inbox — not scattered across panes, badges, and tiles you have to go looking at. The inbox is you as a participant in the same mail system agents use: locus ask from an agent, a Gate waiting on approval, a guardrail trip, a contradiction found at ingest, a workflow goal awaiting sign-off, a finished run needing review.

Silence is the default A session working normally produces nothing. The inbox tells you when something needs you, not when something happened. An item that documents no response is a notification, not inbox work — and notifications go to the activity feed behind the other pill. The inbox also keeps what it resolved, because a queue that empties leaves no record of how long a loop waited on you, which is the one number that says whether the human is the constraint.

Part III

Extending Locus

3.1 Extensions versus plugins — the distinction that governs everything else

Workshop has exactly two subgroups, and the split is not cosmetic. An extension is content Locus authors and materializes. A plugin is an executable integration Locus talks to. They have different contracts, different trust models, and different failure modes.

The first-party roster is deliberately small

Plugin kindFirst-party pluginCanonical id
CLI ToolGitHub CLIgh
HarnessPipi
ProviderOpenAI API / ChatGPT modelsopenai
ProviderClaude modelsanthropic
ProviderOpenRouteropenrouter

That roster is an allowlist of shipped plugins, not a limit on the architecture. A user plugin with a valid trusted manifest is discoverable without a Locus core source change. A non-first-party plugin is either user-installed or absent — it is never silently treated as a built-in.

3.2 Writing an agent definition

An agent is a Markdown file with frontmatter. Not a graph, not a compile step. This is the single biggest simplification in the design: every harness already reads name + description frontmatter over prose, so materializing an agent is close to an identity transform plus a rename.

---
name: reviewer
description: Read-only critic; runs on task completion
harness: any            # or a specific one, when it matters
model_tier: high        # low | medium | high | xhigh — mapped in Settings → Harnesses
                        # a missing tier falls back UP, never down
task_class: research    # code | plan | research — sets retrieval depth; defaults to code
tools: [rg, gh, cargo]  # allowlist, resolved against the marketplace index
skills: [audit-code]
rules: [no-secrets]
memory:
  scope: project        # agent | project — never cross-project
  write: propose        #   none    cannot write memory at all
                        #   propose writes land in the probation buffer for the keeper
                        #   direct  writes straight to the store — the keeper only
---

You review code you did not write. Find the defect, not the style...

The five rules that bind an agent definition

RuleWhy, and what it costs you
tools is enforced, not advisoryIt is the container's install set and the allowlist. A tool absent from the list is absent from the image, so the agent cannot reach for it. Changing the list rebuilds locus/agent-<hash> and invalidates the prefix cache; editing the prose below rebuilds nothing.
Immutable once referencedAn edit creates a new version; a run pins the version it used. Editing builder while builder@4 is running does not change what that run is doing.
An unresolvable tool fails at saveNaming an entry absent from the marketplace index is rejected at save, with the name given — not at run time in a container.
Composition moves to workflowsAn agent does not nest others structurally. It may call locus agent invoke at runtime if that is in its tool list — bounded in the core at depth 3 and fan-out 4, which a workflow may lower and never raise. Depth 3 × fan-out 4 is at most 21 containers, which one machine survives; depth 4 is 85, which it does not.
Definitions live in PostgresImport and export as .md, so a definition can be reviewed in a PR or copied between machines. Export must re-import to an identical definition.

Permissions are declared in two places, and the second may only narrow

Set onDeclaresRule
the agent definitiontools — the install set and the allowlistthe baseline; absent from the list means absent from the image
the workflow's Agent nodea tools subset, a network tier, and write scope for this rolesubtracts only. A node can take the reviewer's write access away; it cannot grant a capability the definition did not have

Narrowing-only matters because the definition is what was reviewed. If a graph could widen, every workflow would be a place to re-grant privileges, and reading an agent would stop telling you what it can do. Enforcement is the container, not the harness.

3.3 The other seven extension types

One three-pane editor serves all of them — a type is a fixture switch on the component, not eight components. Frontmatter field kinds are inferred from the field name through one shared table: a name ending in _tokens renders number, tools and roles render chips, a name whose value set the registry can enumerate renders select, a boolean-named field renders toggle, everything else renders text.

TypeThe invariant a test has to hold
skillsLazy-loaded. A budget_tokens field refuses to materialize the skill above that cap. Downgrade inlines the description into base context and loses lazy loading.
rulesOne glob per rule — a second match is a second rule, not a second glob. A priority field orders overlapping matches. The most downgraded type: concatenated into base context, firing on every file.
base-contextExactly one per project. Native everywhere — it is the fallback every other downgrade lands in. Over budget means something upstream was downgraded and should be fixed there.
commandsArgument-taking prompt templates. A command with no args should be a skill instead. Downgrade materializes it as a skill, losing argument validation.
hooksOne event, a threshold, a timeout, and an on-error choice ending in exit 0 / log / continue. A hook that fails a run has turned an optimisation into an outage.
output-stylesExactly one active per harness. A roles checklist decides which roles get which style. The largest single downgrade in the system when merged into base context.
lintersNative 0 / downgraded 0 by design — a human-and-CLI surface (locus lint), not materialized into any harness, so there is nothing to downgrade. A violation choice of warn or fail; a rule nobody can fail is a preference.
Hooks log and inject. They never think. A hook cannot reuse the agent's LLM, and it fires on every tool call — so any model call inside one taxes the whole run. Two rules follow: the injection path carries a 100ms timeout and emits nothing on expiry, and the logging path never touches the socket synchronously — it appends to a local buffer and returns, with a background flush. Output must not begin with {, which some harnesses parse as JSON rather than as context.

3.4 The plugin contract

Every CLI-tool, harness, and model-provider plugin has a trusted manifest and one executable speaking JSON-RPC 2.0 over stdio, in any language. The manifest envelope is deliberately small.

# plugins/<id>/manifest.toml
protocol     = "locus.plugin.v1"
kind         = "harness"             # cli_tool | harness | provider
id           = "pi"
version      = "1.0.0"
executable   = "locus-plugin-pi"
capabilities = ["harness.session", "harness.materialize"]
permissions  = ["model_catalog"]

What the host does, and refuses to do

Rejects a protocol or version mismatch before dispatching any callGet protocol = "locus.plugin.v1" right or nothing runs
Rejects malformed or required-unsupported capabilitiesDeclare what you actually implement; a harness must expose at least harness.session

3.5 Writing a harness plugin

A harness plugin is the largest of the three, because it has both halves of the contract: a descriptor that says where every extension goes, and capabilities that say how a session is launched and how its events arrive.

Step 1 — the descriptor

The first-party Pi descriptor is the reference entry. Every field is mechanism; none of it is policy.

# harnesses/pi/pi.toml
name   = "pi"
binary = "pi"
detect = ["--version"]           # runs at IMAGE BUILD — its job is to fail the build
                                # when the binary is missing, not to find one on your host
materializer = "pi/materialize"  # hooks and rules are TypeScript here, not files

[image]
base = "debian:bookworm-slim"

[launch]                         # how to start ONE session in ONE run
argv = ["--print"]
tui  = false                     # REQUIRED false, enforced by the registry

[config]

[telemetry]

[models]                         # mechanism only — no model routing here
flag      = "--model"            # how a model is passed to THIS harness
list_argv = []                    # optional: how to ask it what it has

[layout]                         # ALL EIGHT, and where THIS harness reads each
agents        = { via = "dir",  dir = "/locus/config/agents",  format = "markdown+frontmatter" }
commands      = { via = "dir",  dir = "/locus/config/prompts", format = "markdown+frontmatter" }
hooks         = { via = "plugin", emits = "/locus/config/extensions/locus-hooks.ts" }
linters       = { via = "dir",  dir = "/locus/config/linters", format = "shell+markdown" }
output-styles = { via = "dir",  dir = "/locus/config/output-styles", active = "brief-bright-gone" }
rules         = { via = "plugin", emits = "/locus/config/extensions/locus-rules.ts" }
skills        = { via = "dir",  dir = "/locus/config/skills",  format = "markdown+frontmatter" }

The failure this file exists to prevent is silent An omitted extension is refused at registration, with a message naming it. The worst failure mode in this whole class of tooling is a file that is "present, plausible, and loaded by nobody" — the tree is written, the run starts, and nothing loaded. Pi's own descriptor carries a comment recording exactly such a trap: never write to a commands directory, because pi renames <home>/commands to prompts on startup, so writing the old name silently moves the tree.

Step 2 — pass locus harness lint

The lint refuses six things, and each corresponds to a way a capability quietly fails to arrive:

RefusedBecause
an undeclared extensionan omission is indistinguishable from an unsupported capability
an unknown via strategythere are exactly six, and core writes what they return
tui = trueit breaks the one-session-per-run mapping everything depends on

a source other than acpACP is the only transport; the old four-source table is retired
a downgrade with no weaker_than_nativea capability you believe in but do not have is worse than one you know you lack

Step 3 — model routing is mechanism here, policy in the app

An agent asks for model_tier: high. The descriptor supplies only how a model is passed and how to enumerate what exists. Which model high means lives in core.settings, keyed by harness and tier, and is edited in Settings → Harnesses. Three rules make it safe to leave half-filled:

  • A missing tier falls back UP, never down. An agent asking for xhigh on a harness with no xhigh gets high. Falling down would quietly answer a hard question with a cheap model, and the result would look like a bad agent rather than a bad setting.
  • Unset means the harness's default. With no mapping at all, no flag is passed — a harness that was never configured still runs. A new harness is usable the moment it is registered.
  • The resolved model id is recorded on the run, not the tier — so spend and verify pass rate are attributable to what actually answered.

Step 4 — declare capabilities, not a name

The harness contract is capability-based rather than a fixed method list. The minimum for selection is harness.session; everything else is negotiable.

CapabilityRequiredCovers
harness.sessionyesthe minimum session capability needed for selection
harness.launchoptionallaunch mechanics beyond the descriptor's [launch]
harness.eventsoptionalsession events; all supported events map to the canonical ACP vocabulary
harness.materializeoptionalthe plugin strategy — return the files to write
model discovery, permissions, resume, checkpoints, usageoptionaldeclared as needed; absence is recorded, never inferred

A harness may implement native ACP, an ACP adapter, or a materializer-backed configuration. Adding a capability must never require a new core match on the harness id — core validates the schema, routes the request, and preserves unknown optional data for diagnostics.

3.6 Writing a provider plugin

A provider is where a credential is configured, and it holds a reference, not a key. The record carries an identifier, an authentication method, an OS-keychain reference, an optional base_url, verification metadata, and a curated model catalog whose aliases are what every model selector displays.

#!/usr/bin/env python3  —  a complete provider plugin, minus error handling
import json, sys

MODELS = [{"id": "claude-sonnet-4", "alias": "Sonnet"},
          {"id": "claude-opus-4",   "alias": "Opus"}]

def emit(req, result):
    print(json.dumps({"jsonrpc": "2.0", "id": req.get("id"), "result": result},
                     separators=(",", ":")), flush=True)

for raw in sys.stdin:
    req = json.loads(raw); m = req.get("method")
    if m == "plugin.initialize":
        emit(req, {"protocol": "locus.plugin.v1",
                   "capabilities": ["provider.models", "provider.verify", "provider.aliases"]})
    elif m == "plugin.describe":
        emit(req, {"protocol": "locus.plugin.v1", "kind": "provider", "id": "anthropic",
                   "version": "1.0.0", "schema_versions": {"plugin": "v1"},
                   "capabilities": ["provider.models", "provider.verify", "provider.aliases"],
                   "permissions": ["keychain_reference"]})
    elif m == "plugin.health":    emit(req, {"ready": True})
    elif m == "provider.models": emit(req, {"models": MODELS})
    elif m == "provider.verify": emit(req, {"status": "unverified"})
    elif m == "plugin.shutdown": emit(req, {"stopped": True}); break
The one thing a provider plugin must never do Return, log, cache, or accept a raw secret. Postgres stores the keychain_reference; the key never enters a row, a repository, an artifact, a log line, or a container. The host broker resolves the reference only at the egress boundary. A provider plugin that handles a key has broken the single claim the whole credential model rests on.

3.7 Writing a CLI-tool plugin

Two artifacts, and they do different jobs. The marketplace manifest is the resolver's input — it validates an agent's tools list and supplies the one-line catalog entry. The plugin executable supplies install, verify, docs, and digest capabilities.

# index/gh.toml — the marketplace manifest
name    = "gh"
summary = "GitHub's official command-line interface"   # ~15 tokens; this is what
                                                     # reaches an agent's context
install = { brew = "gh" }
verify  = "gh --version"
docs    = "docs/gh.md"                                # fetched ONLY on demand, via
                                                     # locus tools docs gh
caps    = ["source-control", "github"]
Blurbs are a tuning surface, not boilerplate Anthropic reported a 40% cut in task completion time from having an agent evaluate and rewrite tool descriptions. The index is git-backed, so a better description is a commit — and the event store already holds what it would be measured against: how often a tool was reached for, and whether those runs passed.

3.8 Writing a materializer

Only the plugin strategy needs an executable. It is called once per run with the extension set as JSON and returns the files to write — it never writes them itself.

→ materialize { harness, extension, root: "/locus/config",
                entries: [{ name, frontmatter, body }] }
← { files: [{ path, mode, content }] }

Three things fall out of returning data rather than writing it: a materializer is a pure function and therefore testable without a container, a buggy one cannot escape the config tree (core rejects any path that does not resolve under root, and writes nothing), and the same JSON is the fixture for an event-based "did this harness get its rules" test.

Pi's materializer is the reference because a generated TypeScript extension is the furthest a harness gets from copying a directory — it proves the contract at its hardest point:

def materialize(params):
    root = params["root"]
    extensions = params.get("extensions", {})
    files = []
    if "rules" in extensions:
        bodies = [e["body"] for e in extensions["rules"]]     # order as given — sorted upstream
        files.append({
            "path": root + "/extensions/locus-rules.ts",
            "mode": 420,
            "content": TEMPLATE % json.dumps(bodies)})
    return {"files": files}
The determinism checklist — every item is testable, and CI tests them 1. Materializing the same agent twice produces byte-identical trees; diff -r is empty. 2. A materializer that emits a timestamp fails a determinism test. 3. Generated file order and in-file list order are both sorted, asserted independently. 4. A returned path that escapes root is rejected and nothing is written. 5. The config tree is read-only for the run's lifetime — a mid-run write attempt fails. Nothing fails visibly when determinism breaks; the runs just get more expensive. That is why the check is in CI and cache rate is on the dashboard.

An unsigned or untrusted upload is rejected — read-only access is not a meaningful containment boundary for code executed during an image build.

Part IV

Workflows and governance

A workflow is a loop toward a goal, not a one-shot pipeline. It is also the team: its Agent nodes are the roster, each node carries a role, and the edges are the dependencies. There is no separate Team entity, and there is no Job — a workflow subsumes it, and running a single agent ad hoc needs no wrapper at all.

4.1 Six executable nodes

NodeContributes
AgentAn agent definition, pinned by version, plus a role — the definition is reusable, the role is per-workflow. Carries this role's permission narrowing: a tools subset, a network tier, write scope.
TaskA unit of work, optionally sourced from the board.
LoopThe iteration construct: what repeats, and what resets between passes.
ConditionDeterministic routing. No model in the orchestration path — the graph decides, not an LLM.
GateA checkpoint: human, or another agent acting as reviewer.
VerifyThe runnable success criterion. Required — verify is NOT NULL.

What a Condition can say

A small total expression language over facts the run already produced — no code, no model, no I/O, and no way to hang the orchestrator:

verify.passed · verify.exit_code · iteration · elapsed · tokens.used
events.count(tool_error) · events.last(kind) · artifact.exists(kind)
task.status · mail.pending

with  ==  !=  <  >  <=  >=   ·   and  or  not   ·   parentheses

Every operand is a column, so a Condition is a WHERE clause against the run — evaluable in microseconds and reproducible from stored events. Anything it cannot express is a Gate, which is to say a decision that deserved a person or an agent rather than an operator.

4.2 Governance — what sits outside the graph

Where Verify runs, and why it matters In a fresh container from the agent's own image, on the run's branch — never in the agent's container. Two reasons, and they are the same reason: the agent's container may already be gone, and its filesystem holds whatever the agent did outside git. A check that passes only on the machine that made the change has verified nothing. The command comes from the task or the node, the exit code is the result, and stdout plus stderr are captured as the evidence the board requires for Done.

4.3 Guardrails

Each is borrowed from a measured failure in an existing tool. Defaults apply to any agent run; a workflow may tighten or relax them, and they are what make leaving a loop unattended defensible.

GuardrailDefaultWhy
max_iterations8Agents loop endlessly retrying the same broken approach without a hard stop
Forced reflection before retryon"What failed? What specific change would fix it? Am I repeating myself?" — reported to substantially cut stuck agents
Kill-and-reassign after 3 stuck iterationsonA fresh context beats a confused one
Waiting ≠ idle—A run carries a waiting state with a reason — ask, mail, debug-paused, gate — and idle counts only time outside it. One mechanism, four callers. Without it every deliberate block reads as a stall
Idle detection60sNo event on the run's stream for 60s while not blocked. The tile gets an idle icon and a toast fires once per idle stretch, never repeatedly
Wall-clock ceilingnoneOptional; a loop that cannot finish overnight should stop, not run to morning
Token budgetnone — optionalWhen set, auto-pause at 85% and notify rather than draining silently
A budget is optional; the accounting is not Token usage by itself reportedly explains 80% of the variance in agent task performance. If that holds even roughly, tokens are the strongest single predictor of whether a run went well — and a run that passes verify on four times the tokens is a worse run wearing a green tick. So every run carries usage whether or not a ceiling was set, agent trust is weighted by tokens per passing run, and the dashboard reports both.

Pause means the loop stops being fed, not that a process is frozen. The supervisor lets the current turn finish, holds before the next iteration, and notifies; the container stays up so its state is inspectable. SIGSTOP on a harness mid-request would leave sockets half-written and a model call in flight — a worse problem than the spend it saved.

4.4 When Verify fails, classify before retrying

Every guardrail above answers a failed iteration the same way: try again, with reflection, then give up. That is wrong for at least half of failures. Locus routes every failure through a four-way arbiter first, and each class has a different corrective action.

The classification is a column on the iteration, so spec-gap rate and ambiguity-detection rate are queries — and a workflow that keeps producing spec gaps is visibly a planning problem rather than a builder problem.

4.5 Independence is structural, not requested

Role contamination is refused at compile time. One agent definition may not hold both the builder and the tester role in one workflow, and the reviewer may not be the implementer. This belongs in graph validation beside cycles and missing verify — not in a convention someone follows. A verifier that wrote the code inherits its assumptions, and a graph that quietly allows it produces reviews that agree with everything.

RegimeMechanismCatchesCannot catch
Independence-basedone agent implements, another writes tests — both from the requirement, neither seeing the othercontract violations, behavioral bugsanything the requirement never said; shared model blind spots
Attention-basedone model directed into separate reviewer roles — security, architecture, product, QAstructural, product, and UX problemsit is not independent, so a shared misreading survives

Locus can enforce independence structurally, which is the part most setups only ask for politely: separate containers, separate sessions, no shared conversation, no shared short-term memory — all already true — plus the one the git model makes possible: the tester clones the branch at base, before the builder's commits. A verifier that cannot see the implementation cannot adopt its assumptions.

4.6 Worked example — builder, tester, reviewer

  1. Author the roster. Drop three Agent nodes. Each pins a definition by version and carries a role. Narrow the tester's tools to read-plus-test; narrow the reviewer's write scope to none.
  2. Draw the dependencies. An edge from builder to tester is the dependency. When the workflow creates board tasks, that edge becomes the tasks' blocked_by relationship — declared once, visually, rather than drawn on the canvas and re-entered on the board.
  3. Add Verify. The runnable check. It is NOT NULL, so the graph will not compile without it.
  4. Write Governance. The goal is the guiding statement and the termination condition. Add guardrail prompts and success criteria; anything the core cannot check becomes a gate that reaches your inbox with the evidence attached.
  5. Approve the goal. That is the gate. Then it runs unattended: the tester starts the moment the builder's task completes, and the run stops on max_iterations when the goal is unreachable, with the live overlay showing which iteration tripped which guardrail.
The Ralph loop is a preset, not the only shape pick → act → validate → commit → reset is expressible in these nodes already: a Loop whose reset starts a fresh run in the same session, a Verify as the validate step, and Governance's goal as the termination condition. locus ralph --goal … --verify … runs one without opening the canvas, and dropping the preset onto the canvas expands it into ordinary nodes so it can be edited rather than configured. Two honest notes: it is token-hungry by construction — a fresh context every pass is the point — and it is only as good as its verify, because a loop iterating against a weak check converges confidently on the wrong thing.

The cost of deterministic routing, stated plainly: a workflow cannot re-plan itself mid-run. The lead is the graph you drew, not what a model decided this run, which is what makes a run reproducible and debuggable. If dynamic decomposition turns out to be needed, the fix is an agent that authors a workflow and submits it for goal approval — not a model in the execution path.

5.2 Backup and restore

With board, wiki, memory, and mail living only in Postgres, losing the volume loses work no reindex can rebuild. locus backup            # dumps the nine schemas AND the artifact blob tree together
locus restore --drill   # restores into a SCRATCH database, asserts row counts against the source
locus rebuild           # regenerates every projection from log.entries — never touches the carve-outs

locus memory forget <id>traced back to its writer, then deleted

Mail and coordination

locus mail send|list|read|reply|drainagent ↔ agent, Rust-native
locus mail waitblocks with a 15-minute default timeout, then returns empty. Sets waiting, so it never reads as idle
locus ask <question>escalate to the human; blocks, and appears in the inbox
locus handoff <agent> --why …transfer ownership: ends this session, opens the successor's on the same task and branch
locus agent invoke <name>@<version>a nested agent: own container, own clone. Depth 3, fan-out 4

Board and wiki

locus task list|show|move|assign|commentthe board, agent-driven. Done requires evidence
locus wiki search|read|write|historyrevisions attributed to the run
locus wiki ingest <path|url>read a document into typed pages; flags contradictions at ingest
locus wiki query <question>synthesize an answer, filed back as a synthesis page so it is asked once
locus wiki lintorphans, broken links, missing entities, unsourced assertions

Real tools, not a shell

locus lsp def|refs|hover|symbols|rename|diagnosticssemantic navigation over this run's clone. An agent grepping for a symbol reads ten files to answer what one LSP call answers exactly — cheaper in tokens and correct on overloads, shadowing, and re-exports
locus debug start|break|step|stack|vars|evalDAP. The session lives in the core, keyed by run; the CLI holds nothing. break --log is a logpoint: it prints and keeps running
locus browse open|click|fill|press|assertthe project browser, one Playwright context per run. assert exits non-zero with structured JSON, so a Verify node can gate on it
locus browse screenshot|record|console|networkscreenshots and recordings land as artifacts automatically. console and network matter more than pixels — a failing UI usually explains itself in text
locus svc up|down <name>start a project service container. Agents get no Docker socket
locus tools list|docs <name>the allowlisted catalog, and a full page on demand
locus lint [--changed|--only NAME]this project's linters — the one extension no harness reads. Called by the agent before it commits, and by a workflow's Verify node; never from a hook, which would tax every tool call

Artifacts and run state

locus artifact put <kind> <path>publish a plan, diagram, or image for review
locus artifact get <id> [--for-context]--for-context returns OCR text or a downscaled frame, never the raw bytes
locus artifact commentsfeedback left on your artifacts, threaded — a comment steers the agent that made it
locus run status|artifactsthis run's own state
Two rules that apply to every verb above Debugging advice is logpoints before breakpoints. break stops the world, and an agent that stops the world then has to remember to continue it — a stopped process nobody resumes looks exactly like a hung run. Auto-waiting, not sleeps. Playwright waits for actionability by default; an agent writing sleep 2 is a flaky test being born.

Glossary

TermDefinition
ACPAgent Client Protocol — JSON-RPC 2.0 over stdio, LSP-for-agents. The only agent-session transport in Locus.
Agent definitionMarkdown plus frontmatter, versioned in Postgres. Immutable once a run references it.
ArbiterThe bounded agent that classifies a verify failure as Bug, Spec gap, Noise, or Ambiguity before anything retries.
ArtifactA structured deliverable — plan, diff, diagram, image, recording, walkthrough (review kinds) or finding, payload (reference kinds).
AutorunA per-project tri-state switch — on, off, suspended — letting agents pick up their own work. Throttled by review slots, not by agent count.
Base contextThe always-loaded instructions every session starts with. Exactly one per project; the fallback every downgrade lands in.
Canary tokenA secret string in the materialized config that must never appear in output. If it does, the system prompt leaked.
Carve-outA column that cannot be folded from the log because a model or a clock produced it: embeddings, and decay/confidence.
DispatchThe durable queue between a card being ready and a run being started. Supervisor state, not UI state.
DowngradeAn extension materialized by a weaker mechanism than the harness natively offers. Must carry weaker_than_native naming the loss.
ExtensionOne of eight authored content types materialized per run into whatever a harness reads.
GateA checkpoint node — human, or an agent acting as reviewer. Also what an uncheckable success criterion becomes.
HandoffA structured payload transferring ownership: goal, done, remaining, attempted, decisions, open. Not mail, not invoke.
HarnessAn agent CLI, registered as a plugin. Pi is the only first-party one.
Interact sessionA session with no board task: open, promoted, or discarded.
KeeperThe ordinary agent definition that consolidates memory on genuine project idle. The only thing with direct memory-write access.
Locatorlocus://<project>/… — the one address space every navigation path resolves through.
MaterializerThe code half of the harness contract. Six strategies; only plugin needs an executable.
Permission posturebypass (default; a permission request is an alarm) or gated (a request blocks as a visible human action). Selected at dispatch, pinned on the run.
PluginAn executable integration — cli_tool, harness, or provider — speaking JSON-RPC 2.0 over stdio. Data only, never UI.
ProjectOne or more repos, plus the board, wiki, and memory that span them.
ProviderWhere a credential is configured. Holds an OS-keychain reference, never a key.
Review slotOne change you have not read yet. The unit autorun is rate-limited in.
RunOne container lifetime = one ACP conversation. Bounded by the container exiting.
SessionA durable, named thread of work with one agent. Bounded by you closing it. The thing that survives a reset.
Specialization recordA domain's accumulated requirements (payments demands idempotency keys, …), stored as a wiki concept page and injected into synthesis above a confidence threshold.
Stream positionagents.events.stream_pos — monotonic per project, assigned by the core rather than a Postgres sequence.
VerifyThe runnable success criterion. NOT NULL on every workflow, and run in a fresh container from the agent's image on the run's branch.
WalkthroughThe artifact generated on session completion: a concise summary of what changed, screenshots and recordings inline. The actual answer to "six agents ran overnight, now what."

How Locus is tested Event-based. Every run normalizes into the same event vocabulary regardless of harness, capture path, or container — so a test is "run this, assert these events appeared." That works identically across the first-party Pi harness and any trusted user harness plugin, and needs no test-only instrumentation, because the substrate is the one telemetry already requires. Unit tests cover the pure parts; everything above them asserts on the event stream.
